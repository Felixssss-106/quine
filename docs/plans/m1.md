## 2. 前置调研：Android 上执行二进制（M0 时期标记的最大风险）

M0 开局就标过这个风险：「Android 10+ 对从应用私有目录执行二进制有 SELinux 限制，
直接决定 proot 沙箱走哪条路，也影响 targetSdk」。本轮把它从猜测变成了证据。

### 实测（AVD `AILifeTest`，Android 16 / API 36）

```bash
adb shell "run-as com.quine.app sh -c 'cp /system/bin/toybox ./echo && chmod 755 ./echo && ./echo HELLO'"
# → HELLO_FROM_APP_PRIVATE_DIR，EXIT=0
```

**执行本身没有被禁。** rootfs 展开在应用私有目录、从那里 exec 目标二进制，这条路可行 ——
这正是 proot 方案成立的前提。

> 踩坑提醒：第一次用 `./qp_test echo hi` 会报 `toybox: Unknown command`，
> 那是 busybox/toybox 的 **multi-call 派发行为**（按 argv[0] 认命令），不是权限拒绝。
> 权限被拒会报 `Permission denied` 或退出码 126。别被误导。

### 真正的约束在打包，不在执行

1. 二进制必须以 `libxxx.so` 命名放进 `jniLibs/<abi>/`，否则 **release 构建不会打包进去**
2. `AndroidManifest.xml` 里 `android:extractNativeLibs="true"`
3. 从 `applicationInfo.nativeLibraryDir` 执行
4. 依赖的 `.so` 要一起打进去，否则报 `error while loading shared libraries`；
   用 `LD_LIBRARY_PATH` 或 `patchelf` 改名处理（`libs/` 目录不接受 `libnettle.so.8` 这类带版本号的命名）

### 已闭环：API 29–33 也验证过了（2026-09-19 补）

装了 API 29（Android 10）镜像并建了 AVD `QpApi29`，在**两个 API 上都通过**：

| 场景 | API 29 / Android 10 | API 36 / Android 16 |
|---|---|---|
| 应用主目录里 exec ELF | ✅ | ✅ |
| `files/rootfs/bin/` 子目录里 exec（真实 rootfs 布局） | ✅ | ✅ |
| 带 `LD_LIBRARY_PATH` exec | ✅ | — |

```bash
adb shell "run-as com.quine.app sh -c 'mkdir -p files/rootfs/bin && \
  cp /system/bin/toybox files/rootfs/bin/echo && chmod 755 files/rootfs/bin/echo && \
  files/rootfs/bin/echo HELLO_FROM_ROOTFS_BIN'"
# → HELLO_FROM_ROOTFS_BIN，EXIT=0
```

**所以第 ② 个决定不再需要**：minSdk 29 → 36 行为一致，沙箱按统一方案实现即可，
不用写分支、也不用降级提示。复现环境：AVD `QpApi29`（`system-images;android-29;default;x86_64`，pixel_4）。

### 仍待验证

- 真机（Android 14+）上的一致性 —— 模拟器与真机 SELinux 策略可能有差异，装机前建议真机复测一次

### ③ 提议的三件真事

直接取简报里已经写好的验收标准，避免另起炉灶：

1. **改真文件 + 一键回滚** —— 在授权目录里让它改一个文件（例如整理一份笔记），
   改坏能一键回滚（简报 §3.1 验收）
2. **跑命令 + 取回产物** —— 让沙箱跑一段脚本，把结果文件取回授权目录（简报 §3.4 验收）
3. **批量改动有预览且可取消** —— 改多个文件前先给 diff 预览，能取消（简报 §3.1 验收）

这三件覆盖了 M1 的全部能力面（文件写 + 快照回滚 + 命令执行 + diff 预览），且都能在真机上手验。

## 4. 模块变更建议

沿用 M0 的依赖纪律：`app → feature-* → core-*`；feature 之间不互相依赖；`core-loop` 不感知 `core-storage`。

| 模块 | 变更 |
|---|---|
| `core-sandbox`（**新增**） | proot 生命周期（下载/解压/校验/就绪）、进程管理（会话隔离、超时与 kill）、常驻 stdin/stdout 通道、文件通道（沙箱路径 ↔ 应用私有目录映射） |
| `feature-tasks`（**新增**） | 任务列表（运行中/已完成/失败分组）、任务详情时间线 + 五件套内联 |
| `core-tools` | 新增写族工具 `fs_write` / `fs_list` / `fs_search` / `fs_diff`、`shell_run`；**写入前强制快照** |
| `core-storage` | 新增 `TaskRun` / `TaskStep` / `Snapshot` 表（简报 §2.6 草案）；快照内容寻址存储 |
| `core-design` | 五件套组件：diff 块、终端块（永久暗面）、网页块、屏幕块（M4）、时间线条目 |
| `feature-onboarding` | 补**屏幕二：沙箱初始化**（`page-specs.md` §1，四步清单 + 等宽日志 40 字/秒 + 2pt 细进度条 + 失败态） |

## 6. 风险

- **后台存活**（蓝图 §7 第 ① 风险）：沙箱长任务需前台服务 + watchdog + 任务队列持久化；
  M1 若不做自动化，可先不做前台服务，但**进程被杀要有可见反馈**
- **范围失控**（蓝图 §7 第 ③）：M1 已是大里程碑，建议再砍一刀 —— 比如「双主面」若压力过大，
  可先只做任务面，横屏双栏顺延到 M5 打磨期
- **体积与首启**：rootfs 占用（文档写「占用约 200 MB」）直接影响首屏文案与下载体验，
  与 ① 的发行版选择强相关
